# 06. 게스트 접근 모드 및 실행 소유권 분리

## 1. 개발 배경

기존 서비스에서는 주요 기능을 체험하기 위해 회원가입과 로그인이 필요했다.

프로젝트 시연이나 포트폴리오 검토 과정에서 이러한 절차가 진입 장벽이 될 수 있다고 판단해, **회원가입 없이도 주요 시뮬레이션 기능을 이용할 수 있는 게스트 모드**를 구현했다.

단순히 일부 API를 인증 없이 공개하는 대신, 게스트에게도 제한된 JWT를 발급해 기존 Spring Security 인증 흐름 안에서 접근 권한을 관리했다.

```text
게스트 로그인
→ ROLE_GUEST JWT 발급
→ 허용된 기능 접근
→ 시뮬레이션 실행 소유권 검증
```

---

## 2. 핵심 설계

| 구분            | 적용 방식                |
| ------------- | -------------------- |
| 게스트 계정        | 데이터베이스에 생성하지 않음      |
| 인증 방식         | JWT Access Token     |
| 권한            | `ROLE_GUEST`         |
| 식별 방식         | UUID                 |
| 토큰 유효시간       | 1시간                  |
| Refresh Token | 발급하지 않음              |
| 세션 관리         | Stateless            |
| 접근 제어         | 역할 기반 권한 + 실행 소유권 검증 |

일반 사용자는 데이터베이스의 `userId`로 식별하고, 게스트는 JWT의 `subject`에 저장된 UUID로 식별하도록 구성했다.

```text
일반 사용자
→ userId로 식별

게스트
→ JWT에 포함된 UUID로 식별
```

게스트를 임시 회원으로 저장하지 않기 때문에 일회성 체험 사용자로 인한 불필요한 회원 데이터 누적도 방지할 수 있었다.

---

## 3. 게스트 인증 흐름

게스트는 다음 API를 호출해 Access Token을 발급받는다.

```http
POST /api/auth/guest
```

### 응답 예시

```json
{
  "tokenType": "Bearer",
  "accessToken": "eyJhbGciOiJIUzI1NiJ9...",
  "expiresIn": 3600,
  "role": "GUEST"
}
```

이후 요청에서는 발급받은 토큰을 `Authorization` 헤더에 전달한다.

```http
Authorization: Bearer {guestAccessToken}
```

### 처리 과정

```text
게스트 JWT 발급
→ JwtAuthenticationFilter에서 토큰 검증
→ ROLE_GUEST 인증 정보 생성
→ SecurityConfig에서 API 접근 권한 확인
→ Service 계층에서 실행 소유권 검증
```

일반 사용자 로그인과 달리 게스트 로그인에서는 다음 데이터를 생성하지 않는다.

* 사용자 계정
* 비밀번호
* Refresh Token
* Refresh Token 쿠키

---

## 4. 게스트 접근 범위

게스트는 프로젝트에서 제공하는 데이터를 바탕으로 주요 시뮬레이션 흐름을 체험할 수 있다.

### 허용 기능

* 창고·시나리오·로봇·상품 조회
* 시뮬레이션 실행 생성
* 실행 시작·일시정지·재개·초기화·종료
* 시뮬레이션 배속 변경
* 실행 상태 및 로봇 상태 조회
* 동적 재최적화 요청
* 재최적화 이력 조회

### 제한 기능

* 창고 생성·수정·삭제 및 JSON Import
* 시나리오 생성·수정·삭제
* 로봇·상품·노드·엣지 관리
* 내부 상태를 직접 변경하는 API
* 다른 사용자 또는 게스트의 실행 접근
* 게스트 접근 대상으로 명시하지 않은 API

`SecurityConfig`에서는 게스트에게 필요한 경로만 명시적으로 허용하고, 나머지 API는 기본적으로 일반 사용자 권한을 요구하도록 설정했다.

```java
.anyRequest().hasRole("USER")
```

따라서 새로운 API가 추가되더라도 별도로 게스트 권한을 설정하지 않으면 자동으로 접근이 차단된다.

---

## 5. 시뮬레이션 실행 소유권 분리

게스트에게 시뮬레이션 실행 권한을 제공하면 실행 ID를 알고 있는 다른 게스트가 해당 실행을 조회하거나 조작할 가능성이 있다.

이를 방지하기 위해 시뮬레이션 실행 주체를 일반 사용자와 게스트로 구분해 저장했다.

```text
일반 사용자 실행
→ user_id 저장

게스트 실행
→ guest_session_id에 JWT의 UUID 저장
```

실행 조회나 제어 요청이 들어오면 현재 요청자의 식별자와 실행 소유자를 비교한다.

```java
boolean owned = requester.isUser()
        ? run.isOwnedByUser(requester.userId())
        : run.isOwnedByGuest(requester.guestSessionId());

if (!owned) {
    throw new BusinessException(ErrorCode.ACCESS_DENIED);
}
```

소유권 검증은 다음 기능에 공통으로 적용했다.

* 실행 상태 및 이력 조회
* 실행 시작·중지·일시정지·재개
* 실행 배속 변경 및 초기화
* 로봇과 작업 상태 조회
* 동적 재최적화 요청
* 재최적화 이력 조회

이를 통해 여러 게스트가 동일한 창고를 이용하더라도 각자의 시뮬레이션 실행과 이력을 분리할 수 있었다.

---

## 6. 접근 제어 구조

게스트 접근 제어는 두 단계로 구성했다.

### 1단계: 역할 기반 API 접근 제어

`SecurityConfig`에서 `ROLE_GUEST`가 호출할 수 있는 API를 제한한다.

### 2단계: 실행 소유권 검증

Service 계층에서 현재 요청자가 해당 시뮬레이션 실행의 소유자인지 확인한다.

```text
SecurityConfig
→ 해당 역할이 API에 접근할 수 있는지 검증

Service
→ 해당 사용자가 실행을 소유하고 있는지 검증
```

이 구조를 통해 다음 문제를 방지했다.

* 게스트의 영구 데이터 변경
* 다른 게스트의 시뮬레이션 조작
* 다른 사용자의 실행 이력 조회
* 다른 사용자의 재최적화 요청 및 결과 조회
* 새로 추가된 API의 의도하지 않은 공개

---

## 7. 구현 결과 및 고려사항

게스트 접근 모드를 통해 회원가입 없이도 프로젝트의 핵심 시뮬레이션 흐름을 체험할 수 있게 되었다.

또한 모든 API를 단순 공개하지 않고 **게스트 JWT 인증**, **역할 기반 접근 제어**, **실행 소유권 검증**을 함께 적용해 체험 편의성과 데이터 보호를 모두 고려했다.

다만 게스트는 Refresh Token을 발급받지 않는다. Access Token이 만료되거나 새로운 게스트 토큰을 발급받으면 이전 UUID로 생성한 실행 이력에는 다시 접근할 수 없다.

현재 프로젝트에서는 게스트를 **일회성 체험 사용자**로 정의했기 때문에 이 방식을 선택했다.

운영 환경으로 확장한다면 다음 기능을 추가로 고려할 수 있다.

* 오래된 게스트 실행 데이터 자동 삭제
* 게스트 API 요청 횟수 제한
* 외부 AI 및 재최적화 호출 횟수 제한
* Redis를 이용한 게스트 세션 만료 관리
