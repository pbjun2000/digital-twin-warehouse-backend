# 설계 의사결정 및 기술 검토 기록

## 1. 로봇 위치 데이터 저장 단위

로봇의 실시간 위치를 Redis에 저장할 때 다음 두 가지 방식을 검토했다.

- `x, y` 좌표 단위 저장
- 창고 그래프의 노드 단위 저장

처음에는 로봇의 위치를 더 세밀하게 표현하기 위해 좌표 단위 저장을 고려했다. 하지만 시뮬레이션에서 로봇은 창고 그래프의 Node와 Edge를 따라 이동하므로, 백엔드에서 매 순간 좌표를 생성해 전송하면 데이터 전송량과 상태 갱신 횟수가 증가할 수 있다.

또한 좌표 데이터를 자주 전송한다고 해서 사용자 화면에서 반드시 더 자연스러운 움직임이 표현되는 것은 아니다.

따라서 백엔드에서는 다음 정보만 관리하기로 결정했다.

```text
현재 노드
다음 노드
경로 정보
이동 시작 시각
예상 도착 시각
로봇 상태
```

프론트엔드는 시작 시각과 예상 도착 시각을 기준으로 두 노드 사이의 위치를 보간하여 로봇 이동을 부드럽게 표현한다.

```text
백엔드
→ 노드 단위 상태와 시간 정보 전달

프론트엔드
→ 두 노드의 좌표 사이를 시간 기준으로 보간
→ 화면에서 연속적인 이동 표현
```

이 방식을 통해 백엔드는 그래프 기반 상태 관리에 집중하고, 화면 애니메이션은 프론트엔드가 담당하도록 역할을 분리했다.

## 2. 구조화된 입력과 LLM 사용 범위

모든 요청을 LLM에 전달할 경우 다음과 같은 문제가 발생할 수 있다.

- API 호출 비용 증가
- 응답 시간 증가
- 같은 입력에 대한 결과 일관성 저하
- 잘못된 판단이나 환각 가능성
- 숫자와 제한 조건 검증의 어려움

특히 로봇 장애, 배터리 부족, 경로 차단처럼 이미 형식이 정해진 신호는 LLM이 별도로 판단할 필요가 적다.

따라서 입력 유형에 따라 처리 방식을 분리하기로 했다.

### 구조화된 입력

다음과 같이 의미가 명확하고 형식이 정해진 데이터는 규칙 기반으로 처리한다.

```text
ROBOT_FAILURE
LOW_BATTERY
OBSTACLE_DETECTED
COLLISION_RISK
```

처리 예시는 다음과 같다.

```text
이벤트 유형 확인
→ 재최적화 사유 매핑
→ 현재 상태 수집
→ 최적화 서버 호출
```

### 비정형 입력

관리자가 자연어로 입력하거나 요청의 의미가 명확하지 않은 경우에는 LLM을 사용한다.

예시는 다음과 같다.

```text
출고가 밀리고 있으니 긴급 주문을 먼저 처리해줘
배터리가 부족한 로봇은 제외하고 작업을 다시 배정해줘
통로가 혼잡하니 충돌 위험이 낮은 방향으로 재계획해줘
```

LLM은 자연어 요청을 구조화된 미션 조건으로 변환하는 역할을 담당한다.

## 3. LLM의 역할 범위 제한

초기에는 LLM이 다음 기능까지 담당하는 방안을 검토했다.

- 최적화 가중치 직접 생성
- 로봇별 작업 배정
- 미션 후보 생성
- 최적화 방식 선택
- cuOpt 요청값 생성

하지만 LLM이 거리, 시간, 배터리, 우선순위 등의 가중치를 직접 결정하도록 하면 숫자에 대한 근거와 검증 기준을 설명하기 어렵다.

예를 들어 LLM이 다음과 같은 가중치를 반환하더라도 그 값이 최적이라는 보장은 없다.

```json
{
  "distanceWeight": 0.4,
  "batteryWeight": 0.3,
  "priorityWeight": 0.3
}
```

따라서 LLM이 최종 수치를 자유롭게 생성하는 대신, 사전에 정의한 범위 안에서 정책을 선택하도록 제한하는 방향을 선택했다.

예시는 다음과 같다.

```text
FASTEST
BATTERY_SAVING
COLLISION_AVOIDANCE
PRIORITY_FIRST
BALANCED
```

각 정책에 대응하는 실제 가중치와 제약 조건은 백엔드 또는 최적화 서버에서 관리한다.

```text
자연어 요청
→ LLM이 정책 유형과 조건 추출
→ Policy Engine이 유효성 검증
→ 사전 정의된 가중치와 제한 적용
→ cuOpt 또는 경로 최적화 서버 호출
```

이 구조를 통해 LLM의 유연성은 활용하면서도 실제 최적화 입력값의 신뢰성과 재현성을 확보할 수 있다.

## 4. LLM이 필요한 기능

프로젝트에서 LLM이 반드시 필요한 지점을 검토한 결과, 가장 적합한 역할은 자연어 요청 해석과 미션 조건 생성이라고 판단했다.

### 자연어 기반 창고 운영 명령

관리자는 복잡한 API 입력값 대신 대화형으로 운영 요청을 입력할 수 있다.

```text
오늘 오후 출고 예정인 긴급 상품부터 처리해줘
배터리 30% 이하인 로봇은 충전소로 보내줘
2번 통로를 사용하지 않고 경로를 다시 계산해줘
현재 상황을 요약하고 필요한 조치를 알려줘
```

LLM은 자연어에서 다음 정보를 추출한다.

```json
{
  "intent": "REOPTIMIZE",
  "priority": "URGENT_OUTBOUND",
  "excludedRobotConditions": {
    "batteryBelow": 30
  },
  "blockedEdges": [],
  "policy": "PRIORITY_FIRST"
}
```

이후 백엔드가 값의 유효성을 검증하고 실제 시뮬레이션 또는 최적화 요청으로 변환한다.

### 시나리오 생성 보조

관리자가 자연어로 가상의 운영 상황을 요청하면 LLM이 시나리오 후보를 생성할 수 있다.

```text
로봇 한 대가 고장 나고 긴급 출고 작업이 추가되는 시나리오를 만들어줘
```

LLM은 다음과 같은 시나리오 초안을 생성한다.

```json
{
  "scenarioType": "ROBOT_FAILURE_WITH_URGENT_TASK",
  "robotFailureCount": 1,
  "urgentTaskCount": 1,
  "expectedAction": "REOPTIMIZATION"
}
```

다만 생성된 시나리오는 즉시 실행하지 않고, 백엔드의 검증과 관리자 확인을 거친 후 실행하도록 한다.

## 5. 최종 역할 분담

최종적으로 각 구성 요소의 역할을 다음과 같이 정리했다.

```text
프론트엔드
- 자연어 명령 입력
- 시나리오 및 정책 선택
- 로봇 이동 보간 및 시각화
- 실시간 상태 표시

Spring Boot
- 요청 검증
- 이벤트 처리
- 정책 적용
- 시뮬레이션 및 작업 상태 관리
- Redis, PostgreSQL, Neo4j 연동
- FastAPI와 LLM 서비스 호출

LLM
- 자연어 의도 분석
- 미션 후보 생성
- 정책 유형과 조건 추출
- 운영 상황 설명 생성

FastAPI / 최적화 엔진
- 작업 배정 계산
- 경로 최적화
- 제약 조건 적용
- 재최적화 결과 반환
```

이 설계를 통해 구조화된 입력은 규칙 기반으로 안정적으로 처리하고, 자연어처럼 해석이 필요한 입력에만 LLM을 사용하도록 범위를 제한했다.
